5分間アイドル状態になると、その経路は不通になる

作成日2026-11-17|更新日2026-11-17|技術開発システムとネットワーク
|総文字数:1.3k|読む時間:5分|閲覧数:|コメント数:

10 月 28 日、固定サーバー localhost-1 の元の入口に対して SSH を3回実行した。2回はタイムアウト。LAN アドレス 192.168.9.29 に切り替えると、3回連続で成功し、0.8〜0.9 秒だった。

同じ tailnet、同じマシンで、片方は通り、片方は通らない。違いは、「直結」がここでは Tailscale の NAT パンチスルー経路を指すということで、パンチスルーが成功するとそれは静かになる——数分静かにして、またパケットを送ると、穴を開け直し、また待たなければならない。

上流には一致する報告がある：tailscale/tailscale#20452、アイドル経路での失敗。方向は明快だ。NAT パンチスルーという経路がそもそも不安定なら、それを主経路にしない。

まず三種類を区別する

Tailscale が2台のマシンを接続する経路はおおよそ3種類ある：

  1. 直結（パンチスルー成功、UDP ポイントツーポイント）；
  2. Peer Relay 経由。tailnet 内の、中継を引き受けてくれるマシンが転送する；
  3. DERP へ到達。公式または自前のリレーノード。

日常は 1 で速く動くので、問題は「1 が成立しないその瞬間」にだけ露出する。1 の信頼性を積み上げても（キープアライブ、リトライ）根本は解決しない。できるのは 2 と 3 を両方用意し、フォールバックが公衆 UDP の運任せにならないようにすることだ。

今回は2台のマシンを変更した：

  • localhost-3 公衆 103.11.77.24:40000/UDP、Peer Relay を担当；
  • 予備 VPS 38.207.161.228、443/TCP でプライベート DERP を動かし、80/TCP は証明書検証のみ、3478/UDP で STUN。

管理画面のポリシーは最も狭いものを選んだ。既存の業務と SSH ルールは動かさず、localhost-1 にだけこの2つの中継を使う権限を追加する。変更前の完全なポリシーは tailnet-before.hujson としてバックアップし、作業の最後に JSON エディタから読み戻して最終ファイルとパース比較する——どちらも一致していなければならない。

Peer Relay は誰に設定させるのか

Peer Relay は「入れたら誰かが使ってくれる」ものではない。クライアントが管理画面のポリシーで許可された前提のもと、自分で選ぶ。だから権限は中継側ではなくそれを使うマシンに付ける。2つの中継を localhost-1 の権限に加えたうえで、管理画面がすでにリージョンを配信していることを確認する。

プライベート DERP 側にはリージョン 900 を追加した。公式リージョンはすべて残し、管理画面からの配信後、DERP map は合計29リージョン——足すだけで減らさない。ロールバックはリージョン 900 の1行を削除するだけだ。

DERP ノードは -verify-clients を立て、ローカルの tailscaled がクライアントの現在の tailnet 所属を検証する。証明書は Let’s Encrypt が署名した IP 証明書で、SAN はまさに 38.207.161.228、derper が自分で管理し自動更新する。キャッシュディレクトリ /var/lib/derper/certs/ は診断ログにそのままコピーできない。

WARP と tailscaled はどちらもデフォルトルートを欲しがる

ここが今回いちばん「直したものをまた壊す」場所だ。

WARP クライアントはデフォルトルートを書き換え、tailscaled も自分のルーティングテーブルで出口を選ぶ。両方が自分がデフォルトルートを管理していると思い込むと、Tailscale のトラフィックが WARP トンネルに押し込まれ、中継はかえって通らなくなる。

やり方は、実際の Tailscale ルーティングテーブル 52 に優先ルックアップを1回与える。ポリシールーティングに優先度 5208 を追加し、tailscale0 にだけ WARP ファイアウォールの例外を付ける。他の WARP ルートは引き続き有効で、それ以外は一切触らない。2台のマシンにそれぞれ15秒のタイマーがあり、この例外を守っている：tailscale-warp-coexist.timer。

DERP は証明書の署名が必要で、ACME は公衆網から出て検証しなければならない。この出口は専用のテーブル 65800、優先度 5207 を単独で通り、15分ごとに ACME の現在の IPv4 だけを更新し、他のデフォルト出口は動かさない。

毎日誤報するチェッカー

メンテナンススクリプトが動き出すと「ルール競合」を報告し始めた。調べるとパースの問題だった。ip route は dst と dstlen を別々に出力し、スクリプトは2つのフィールドをそれぞれ比較するので、同じネットワークセグメントは当然永遠に一致しない。

修正は、まずネットワークセグメントを正規化してから比較する。修正後に再実行と定期トリガーをやり直し、2台とも Result=success、ExecMainStatus=0 で、しかも初回インストール時のルートとファイアウォール例外はずっと残っている——「直した」スクリプトにうっかり消されていない。

毎日アラートを出す見張りは、見張りがないより悪い。人に無視することを覚えさせるからだ。

検証はバイトまで

設定後の最初の時点で、3回の SSH はすべて通った。9.00 秒、7.96 秒、9.35 秒。LAN より10倍遅いが、通った。

これで終わりにはできない。「さっきの数回の成功」はアイドル後に通ることを証明しないからだ。そこで検証は能動的な逆方向で行う：

  • サーバー側の逆方向プローブで接続を起こす；
  • 103.11.77.24:40000 の Peer Relay 経由で 262144 バイトを完全に転送し、SHA256 8a39d2ab...、両端で一致；
  • 中継セッション統計で双方向に実際のデータがあることを確認。

そのうえでアイドルテスト：接続を5分以上静置し、その間 ping も起こしもせず、最初のリクエストで直接 262144 バイトをダウンロードする。完全に受信し、所要時間は約 28.84 秒、チェックサムは一致。

DERP 側：公衆 HTTP は 204 を返し、HTTPS /derp/probe は 200 を返し、クライアント証明書の検証結果は 0、発行者は Let’s Encrypt YE1。Mac 上で tailscale debug derp 900 を使って接続が確立できることを確認した。

迂回できなかった警告

公式 derpprobe は IP 証明書に対して二つの警告を出す。空の SNI、そして七日未満の短期証明書だ。

どちらも実在する。緑にするために証明書検証を切るのではなく、「転送効果は実際の接続テストを基準とする」と明示した。途中で force-prefer-derp 900 を試して強制的にプライベート DERP を通すこともした。確かに有効だが、これはデバッグ用の好みであって長期設定にはできないので、終了時に既定へ戻した。

バージョンについても一言残しておく。三台の Tailscale はすべて 1.104.2 で、公式は 10/28 に Tailscale SSH のセキュリティ修正を含む 1.104.4 を出した。三台とも内蔵の Tailscale SSH は元々切っていて OpenSSH を使っているため、今回は上げなかったが、今後のアップグレードでは同じバージョンに合わせた derper を同時に再構築する必要があると記録した。

境界

  • プライベート DERP は公衆 TLS、クライアント接続、設定配布まで検証したが、プライベート DERP のみで動かす完全な隔離への切り替えは行っていない。“peer-relay-upload-result.json” のデータは Peer Relay のもので、DERP 転送の証拠には使えない。
  • コールドスタートが一度成功したからといって、アイドル時の故障が消えたわけではない。日常使用の中で引き続き見ていく必要がある。
  • マシンに IPv6 はないので、診断時の「適切なアドレスなし」という表示は IPv4 が通らないことを意味しない。

ロールバック手順は記録に四項目書いた。バックエンドポリシーを tailnet-before.hujson に戻す、localhost-1 でプロキシ設定を撤回する、localhost-3 で Peer Relay を停止し UDP 許可を回収する、予備 VPS はバイナリを残してサービスだけ止める。短いホスト名の SSH 公開鍵エイリアスは ssh-keygen -R localhost-1 で取り消す。

締めくくり

この一連の作業の後、元の入口、LAN 内の入口、短いホスト名、完全なドメイン名のいずれからもログインでき、厳格なホスト検証は常に有効のままだ。localhost-1 のホスト鍵を追加する前に、DNS が指す先が確かにそのマシンであることを確認し、そのうえで既に信頼済みの同じ公開鍵をエイリアスとして追加した。

本当に役立つ結論は一言だけだ。ホールパンチングが不安定なときは、もうホールパンチングを直そうとするな。「たとえ永遠に貫通できなくても動く」ところまで退路を敷き、それを繰り返し検証せよ。
