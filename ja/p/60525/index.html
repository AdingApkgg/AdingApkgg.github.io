削除する前に一度読み、削除した後にもう一度読む

作成日2026-11-17|更新日2026-11-17|技術開発デプロイと運用
|総文字数:1.2k|読む時間:5分|閲覧数:|コメント数:

アーカイブのバックエンドを Windows からオブジェクトストレージに切り替えた後も、そのマシンには古い経路が一式残っていた。スケジュールタスク、H ドライブのディレクトリ、Caddy の root ディレクティブ、失効した認証情報のコピー、誤って作った WSL ビルドディレクトリ。

サービスはもうこれらを使っていないが、「使っていない」と「影響がない」は別物だ。Caddy のその root * H:/wg はすでに存在しないディレクトリを指しており、設定は動き続けている。次に reload したときが、現実の失敗の機会になる。

まずは読み取り専用の棚卸しで範囲をはっきりさせ、それから削除する。

棚卸しは、まず「棚卸しきれていない」ことを認める

再調査の対象は、以前の作業ディレクトリ、H ドライブのルート、WG- / WVN- のスケジュールタスク、既知の共有 Caddy 設定、本機の関連する起動エントリだけだ。全盤スキャンではなく、的を絞った棚卸しである。

数え上げたものは次のとおり：

  • Windows 上の WG- / WVN- スケジュールタスク 31 件。18 件が Disabled、13 件が Ready で、Running はない。アクションはすべて、すでに消した H ドライブのディレクトリを指している。13 件の Ready のうちトリガーを持つものは 1 つもない——Ready は自動実行を意味しない。それらはシステムに残ったままの一度きりの登録にすぎない。
  • C:/ProgramData/CaddyWG/Caddyfile の 14 行目 root は存在しない H:/wg を参照し、42 行目 pem_file は存在しない H:/wg-split-production-storage-20261024/arch-web.crt を参照している。CaddyWG と Cloudflared はどちらも Running / Auto のまま。
  • WSL には /home/i/wvn-build-fallback-20261115 がまだあり、中に jobs、artifacts、workspaces、環境スクリプトが入っている。
  • Alice のマシンには /home/i/webgal-b2-transfer-20261027/.secrets/rclone.conf がまだあり、SHA256 全体が以前削除した失効済みの旧バケット設定と完全に一致する——写し漏れの古い認証情報コピーだ。比較したのはダイジェストだけで、鍵は出力していない。

「未検出」も明記した。H ドライブのルートに wg* / wvn* / .wvn* はなく、本機に一致する LaunchAgent / LaunchDaemon / cron はなく、Alice に一致する cron、systemd unit、旧バケットで動いているプロセスもない。

最後の結論では、あえて「依然として明確な残留がある」と書き、「すべて片付いた」とはしなかった——棚卸しした場所は、棚卸ししていない場所と同じではない。

順序：まずアーカイブし、それから削除する

クリーンアップスクリプトの最初のアサーションは「今回のタスクディレクトリに start マーカーがすでにあれば再生を拒否する」で、2 文目はホスト名の検証だ：

if(Test-Path "$r/start"){throw 'Existing job; no replay'}
if($env:COMPUTERNAME -ne 'DESKTOP-ASUNA'){throw 'Unexpected host'}

次にベースライン。CaddyWG と Cloudflared の 2 つの共有サービスはどちらも Running でなければならない。まず ProcessId を記録し、終了時に 1 つずつ突き合わせて、同じプロセスのままであることを確認する。この 2 つのサービスは今回のクリーンアップの対象ではなく、再起動すると「きれいに削除した」が付随障害になってしまう。

Caddy の変更は「候補を生成 → 検証 → 上書き → reload → 稼働中の設定を読み戻す」という順で進める：

  1. 元の設定を読み、SHA256 を照合し、棚卸しの後に誰も変更していないことを確認する；
  2. 文字列置換で root * H:/wg を削除し、pem_file を存在する証明書に置き換える；
  3. 置換後が原文と同一、または H:/wg がまだ残っていれば、その場で失敗とする；
  4. 候補ファイルを caddy validate、非 0 なら停止する；
  5. 元ファイルをバックアップし、候補を書き込み、caddy reload；
  6. reload が失敗したらディスク上の設定を元に戻す。サービスは再起動しない；
  7. reload が成功したら http://127.0.0.1:2021/config/ をリクエストし、稼働中の設定をシリアライズする。H:/wg を含まず、新しい upstream アドレスを依然として含んでいなければならない；
  8. 最後に 2 つのサービスの PID が変わっていないことを確認する。

7 番目が肝心だ。ディスク上のファイルが正しいことは、Caddy のメモリ上でそれが動いていることと同じではない。ファイルだけを見ていると「reload が効いていない」類のものを見落とす。

スケジュールタスクのほうは、まずエクスポートし、それから登録解除する：

Export-ScheduledTask -TaskName $row.name -TaskPath $row.path | Set-Content -Encoding UTF8 "$taskdir/$($row.name).xml"
Unregister-ScheduledTask -TaskName $row.name -TaskPath $row.path -Confirm:$false

エクスポートの前には、アクションが参照するパスが変わっていないことも確認する。実行中のタスクはそのまま残す。最後に残った ^WG-|^WVN- を数え、0 でなければならず、削除した数は 31 でなければならない。

WSL のあのディレクトリ

それは設定ではなく、誤って作ったビルド用ワークスペースで、残しておいても場所を取るだけだ。

WSL 内で Python を使ってアーカイブする。条件は決め打ちだ。ディレクトリが存在する、シンボリックリンクではない、稼働中の run-build.sh がすでに存在しない、ROLE_DISABLED.md が存在する。再帰中はどんなシンボリックリンクも拒否する。tar は x モード（既存なら失敗）を使い、作成後にアーカイブの SHA256 を計算し、shutil.rmtree の後にディレクトリが本当に消えたことをアサートする。

アーカイブは Windows 側のタスクディレクトリに置き、今回のラウンドの証跡と一緒に扱う。

本機、Alice、あの認証情報

  • 本機では古い作業ディレクトリを 3 つ削除した。監査ディレクトリには共通の SSH 補助スクリプト 1 つだけを残した。
  • Alice では運用スクリプトを 36 個削除し、削除前にスクリプトの証跡をアーカイブした。
  • 失効した rclone.conf のコピーを削除した後、グローバルの rclone には無関係な r2 設定しか残っていないことを確認し、削除した 2 つの旧コピーが復元されていないことも確認した。
  • 一時停止中のローカル監視「WG 拉取状态通知」を削除した。

Alice のマシンで本当に守るべきものはリソースとバックアップであり、削除後に 1,067,041 個の保護対象ファイル、173,316,714,942 バイトについて前後不変の照合を行い、新しいバケットとバックアップディレクトリには一度も触れていない。

クリーンアップのあとにもう一度本番を見る

削除が終わっても「きれいに消えたかどうか」だけを見るのでは足りない。本番が巻き添えを食っていないかも見なければならない。

20 分ほどで一巡の現網確認を行った。health は依然として production/save-cas-b2-20261115-r2、コンテナは Running で OOM も再起動もなく、StartedAt はクリーンアップ前のリリースと一致し、backend は依然として b2-cas、Windows upstream は空。4 本の代表作を Chromium で読み込み、ネイティブな描画が出て、終了。旧キャッシュドメインへのリクエストは 0。3 つのカーネルそれぞれで合成 QA クラウドセーブのアップロード、バイト単位のダウンロード、冪等コミット、履歴復元を実行し、さらに実 WebSocket で 2 ページの送受信を行った。

修正していない例外も一つ残した。Python urllib で公開オブジェクトを取得するとまず 403 が返り、レスポンス本文は CF の error code 1010 だ。同じ URL は 3 つの実ブラウザと、本物の Origin: null コンテキストでは通る。スクリプトクライアントの制約はスクリプトクライアントの制約として記録し、ついでに CF をいじることもせず、「修正済み」と書くこともなかった。

確認範囲として記したのは「代表サンプルにリグレッションは見られない」であり、「全作品クリア」でも「3 カーネルの完全マトリクス」でも、B2 の実際のコールドダウンロード性能でもない。

締めくくり

スクリプトの失敗分岐はとても単調だ。どのアサーションが一つでも通らなければ catch に飛び、エラー行番号付きで error.json を書き、exit を書き、finally で transcript を止める。「残りのステップを続行する」という選択肢はない。

クリーンアップのようなものは、漏れることより、漏れたことに気づかないことが一番怖い。31 個のタスクのうち 30 個目で止まるほうがましで、31 個すべて消し終えてから Caddy が起動しない設定に差し替えられていたことに気づくのは避けたい。
