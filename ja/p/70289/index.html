空のuserdata、デュアルスロットablとinit_bootの位置

作成日2026-11-17|更新日2026-11-17|ツールとシステムフラッシュ
|総文字数:786|読む時間:3分|閲覧数:|コメント数:

アンロックのステップを終えると、画面にはオレンジ色の警告、5秒の待機、そしてシステムへ。ここまではすべて正常だ。

問題はその直後に来る。この記事で記すのは3つの詰まりどころで、それらの共通点はエラーメッセージが指す方向と本当の原因が違うということだ。

「Couldn’t mount file system」はシステムの書き込み失敗ではない

アンロックは data を消去するので、data パーティションは空で、ファイルシステムもまだ作られていない。初めて recovery に入ったとき、下部に出る赤い文字が Couldn't mount file system だ。

system の書き込みに失敗したと誤解して、system を焼き直しに戻りがちだ。だが実際は不要で、system は正常、足りないのは data のフォーマットだ。

対処は、音量キーで Wipe Data を選び（recovery によっては Format Data / Factory Reset と呼ばれる）、電源キーで確定、もう一度選んで確定し、その後 Reboot to system。初回起動には数分かかる。

順序について覚えておくべきことが2つある：

  • フォーマットはシステムを焼いた後に行う。焼く前ではない——書き込みの過程で再び data に触れる可能性がある。
  • コピーしたイメージのディレクトリを sdcard に残さないこと。フォーマットで一緒に消える。

デュアルスロット：片方だけ書くのは後々の禍根

このマシンの abl には _a、_b の2つのスロットがある。

エンジニアリング abl を abl_a にだけ書くと、abl_b は公式バージョンのままになる。デフォルトスロットが A のうちは違いは分からないが、一度ブートが B に切り替わると、2つのスロットの読み込みロジックは同じではなくなる。

ツールはデフォルトで2つとも書く。手打ちでも同じで、両方書いて最後に sync。書く前に ls してファイルがあることを確認する。

同じ理屈は以降のすべての「パーティションへ dd する」操作に当てはまる：書き終えたら必ず現在のスロットを確認する。A/B スロットは「バックアップ」ではなく、2台の交代制のマシンであり、あなたはそのうち1台しか直していない。

「OTA の後、A スロットは空」

ここが最も難しい箇所で、3つのものを同時に踏んでいる。

システム更新がブートを B スロットに切り替えたので、現在のシステムから init_boot を抜き出してパッチを当てる必要がある。抜き出す方法は2つあるように見えるが、どちらも通らない：

  • fastboot fetch：この bootloader は非対応で、Device does not support fetch command を吐く。
  • adb shell dd if=/dev/block/by-name/init_boot of=/sdcard/...：shell が disk グループになく、読み出しは0バイトになる。

すると残る正攻法は2つだけ：6 GB の完全な公式パッケージをダウンロードして展開するか、もう一度一時 root を取得して root 権限で dd により現在のスロットの内容を吸い出すか。後者はそんなに大きなパッケージを落とさずに済むが、代償として一時 root の一連の作業をもう一度全部やらなければならない——しかも終わったらきれいな状態に再起動してからパッチを当てる必要がある。

ここには絶対に外せない判断がある：現在のシステムは B スロットにあり、抜き出すのは _b の内容で、パッチも必ず init_boot_b に焼かなければならない。_a に焼いても何の通知もなく、ただ効かないだけだ。

boot か init_boot か

同じ問題がスマホでは2つの答えになる。機種に独立パーティションがあるかどうかに依存するからだ。

判断基準は汎用的なもので、経験則ではない：

あなたのマシンに init_boot パーティションがあるなら、init_boot を優先して直す；boot パーティションしかない場合にのみ boot を直す。

2台とも init_boot を持っている。スマホもこのタブレットも同じく GKI デバイスだ——ramdisk は init_boot にあり、boot にはカーネルしか残っていない。

この構造が「どこに当てるか」を決める：boot を焼いても画面は点き、起動もする。カーネルは壊れていないからだ。だがパッチは ramdisk 内の init フックで読み込まれる必要があり、boot に当てるのはフックのない場所にイメージを押し込むだけなので、インストール後も「未インストール」と表示されるという現象になる。2台ともこれでそれぞれ2往復を無駄にした（次回詳述）。

状態を確認する2つのコマンド

「良くなったように見える」より信頼できる判断：

adb shell getprop ro.boot.verifiedbootstate   # orange = 已アンロック
adb shell getprop ro.boot.flash.locked        # 0 = 未锁
adb shell getprop sys.boot_completed          # 1 = 已正常开机

バージョンの照合は設定画面の「ロック解除済み」の行ではなく、ro.build.display.id か設定内の完全なバージョン番号を見る。

まとめ

3つの詰まりどころは最後には同じ一言に戻る：まず今どのスロットにいて、どのパーティションを触るのかをはっきりさせ、それからどのコマンドを使うかを決める。

Couldn't mount file system は壊れたシステムに見え、デュアルスロットは「どうせ一緒に書かれる」に見え、fastboot fetch は「コマンド1つの話」に見える。3つの錯覚の共通の結末は、5分の操作を1回の焼き直しに変えてしまうことだ。

技術的ではないが同じくらい重要なもう1つ：アンロック・書き込みから数日のうちはシステム更新を押すな。OTA はパッチを上書きし、スロットを切り替え、ようやく把握したスロットをもう一度ひっくり返す。しかもメジャーバージョンは検証済みの方法までかき乱す。
