删之前先读一遍，删之后再读一遍

发表于2026-11-17|更新于2026-11-17|技术开发部署与运维
|总字数:1.6k|阅读时长:5分钟|浏览量:|评论数:

存档后端从 Windows 切到对象存储之后，那台机器上还留着一整套旧链路：计划任务、H 盘目录、Caddy 里一条 root 指令、一个失效的凭据副本、一个误建的 WSL 构建目录。

服务已经不用它们了，但「不用」和「没有影响」是两件事。Caddy 那条 root * H:/wg 指向一个已经不存在的目录，配置还在跑，只要下次 reload 就是一次真实的失败机会。

一轮只读盘点先把范围说清楚，然后再删。

盘点先承认盘不全

复查只覆盖了此前的工作目录、H 盘根、WG- / WVN- 计划任务、已知的共享 Caddy 配置、本机的相关启动入口。是定向盘点，不是全盘扫描。

数出来的东西：

  • Windows 上 31 条 WG- / WVN- 计划任务，18 条 Disabled、13 条 Ready，没有 Running。动作全都指向已经清掉的 H 盘目录。13 条 Ready 里没有一条带触发器——Ready 不等于会自动跑，它们只是留在系统里的一次性注册。
  • C:/ProgramData/CaddyWG/Caddyfile 第 14 行 root 引用不存在的 H:/wg，第 42 行 pem_file 引用不存在的 H:/wg-split-production-storage-20261024/arch-web.crt。CaddyWG 和 Cloudflared 都还在 Running / Auto。
  • WSL 里 /home/i/wvn-build-fallback-20261115 还在，里面有 jobs、artifacts、workspaces 和环境脚本。
  • Alice 那台机器上 /home/i/webgal-b2-transfer-20261027/.secrets/rclone.conf 还在，整份 SHA256 和此前删掉的失效旧桶配置完全相同——是漏抄的一份旧凭据副本。只比对摘要，没打印密钥。

也明确写了「未发现」：H 盘根没有 wg* / wvn* / .wvn*，本机没有匹配的 LaunchAgent / LaunchDaemon / cron，Alice 没有匹配的 cron、systemd unit 或旧桶活动进程。

最后的结论句特意用了「仍有明确残留」，而不是「全部清完」——盘过的地方不等于没盘过的地方。

顺序：先归档，再删

清理脚本的第一个断言是「本次任务目录里已经有 start 标记就拒绝重放」，第二句是校验主机名：

if(Test-Path "$r/start"){throw 'Existing job; no replay'}
if($env:COMPUTERNAME -ne 'DESKTOP-ASUNA'){throw 'Unexpected host'}

然后是基线：CaddyWG 和 Cloudflared 两个共享服务必须都在 Running，先把 ProcessId 记下来，收尾时逐个比对，必须还是同一个进程。这两个服务不是本次清理的对象，重启它们会把「删了个干净」变成一次附带故障。

Caddy 的改动按「生成候选 → 校验 → 覆盖 → reload → 读回线上配置」走：

  1. 读原配置，核 SHA256，确认盘点之后没人改过；
  2. 用字符串替换去掉 root * H:/wg，把 pem_file 换成存在的证书；
  3. 如果替换完等于原文、或者还剩 H:/wg，直接失败；
  4. caddy validate 候选文件，非 0 就停；
  5. 备份原文件，写入候选，caddy reload；
  6. reload 失败就把磁盘配置换回去，不重启服务；
  7. reload 成功后请求 http://127.0.0.1:2021/config/，把线上配置序列化出来，必须不含 H:/wg、必须还含新的 upstream 地址；
  8. 最后确认两个服务的 PID 没变。

第 7 步是关键。磁盘上的文件对了，不等于 Caddy 内存里跑的就是它。只看文件会漏掉「reload 没生效」这一类。

计划任务则是先导出、再注销：

Export-ScheduledTask -TaskName $row.name -TaskPath $row.path | Set-Content -Encoding UTF8 "$taskdir/$($row.name).xml"
Unregister-ScheduledTask -TaskName $row.name -TaskPath $row.path -Confirm:$false

导出前还要核动作里引用的路径没变，运行中的任务直接保留不动。最后统计剩几条 ^WG-|^WVN-，必须 0，删掉的必须是 31。

WSL 那个目录

它不是配置，是一个误建的构建工作区，留着只是占地方。

在 WSL 里用 Python 打包，条件写死：目录存在、不是符号链接、活动的 run-build.sh 已不存在、ROLE_DISABLED.md 在；递归时任何符号链接都拒绝。tar 用 x 模式（已存在就失败），打完算归档 SHA256，shutil.rmtree 之后断言目录真的没了。

归档落在 Windows 那边的任务目录，跟着这一轮的证据一起走。

本机、Alice、那个凭据

  • 本机删了 3 个旧工作目录；审计目录里只留一个公共的 SSH 辅助脚本。
  • Alice 删了 36 个运维脚本，删之前把脚本证据归档。
  • 失效的 rclone.conf 副本删掉之后确认全局 rclone 里只剩不相关的 r2 配置，删掉的那两份旧副本没有恢复。
  • 暂停中的本地监控「WG 拉取状态通知」删除。

Alice 那台机器上真正要保的东西是资源和备份，删完之后对 1,067,041 个受保护文件、173,316,714,942 字节做了前后不变核对，一次都没碰新桶和备份目录。

清理之后再看一遍线上

删完不能只看「删干净了没有」，还得看线上有没有被连累。

二十来分钟里做了一轮现网复核：health 仍是 production/save-cas-b2-20261115-r2，容器 Running、没有 OOM 或重启，StartedAt 和清理前的发布一致，backend 仍是 b2-cas，Windows upstream 为空。四个代表作在 Chromium 里加载、出原生画面、退出，旧缓存域请求 0。三内核各跑一遍合成 QA 云存档的上传、逐字节下载、幂等提交、历史恢复，加真实 WebSocket 两页收发。

也留了一个没修的例外：Python urllib 抽公开对象先返回 403，响应正文是 CF 的 error code 1010。同一个 URL 在三个真实浏览器和一个真的 Origin: null 上下文里都通过。脚本客户端的限制就记成脚本客户端的限制，没有顺手去改 CF，也没写成「已修复」。

复核范围写的是「代表样本未见回归」，不是「全部作品通关」，不是「三内核完整矩阵」，也不是 B2 的真实冷下载性能。

收尾

脚本的失败分支很单调：任何一条断言不过就跳进 catch，写 error.json 带出错行号、写 exit，finally 里停 transcript。没有「继续执行剩余步骤」的选项。

清理这种东西，最怕的不是漏，是漏了还不知道。宁可 31 个任务只删到第 30 个就停下，也不要删完 31 个之后才发现 Caddy 已经被换成了起不来的配置。
