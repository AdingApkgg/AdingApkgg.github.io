Running KDE on a tablet: you can, but accept the cost first

Created2026-11-17|Updated2026-11-17|Tools & SystemsFlashing
|Word Count:854|Reading Time:5mins|Post Views:|Comments:

After unlocking the tablet, rooting it, and flashing back to the official 306 build, beyond “one more machine I can tinker with,” I wanted it to do some laptop things: LibreOffice, a terminal, a browser, drawing.

First, let’s be clear about what this is: this is a chroot, not native Linux. Android keeps running underneath, competing for memory and throttling the CPU, and graphics go through X11 forwarding rather than direct output. Light office work is passable; don’t count on 4K editing or big builds.

The trade-offs of three paths

  • Native dual-boot (installing Linux on slot B): best performance, but you have to touch the slots. Right after unlocking and just after flashing the official system, the risk of switching slots has to be counted separately — not worth it.
  • Fedora + KDE: people really are doing this on sheng in 2026, but the status is “experimental” — the repo is cobbled together on the fly by GitHub Actions rootfs.img, and the author was still changing it ten hours ago. Installing it is not a matter of grabbing the next ISO.
  • Termux + chroot: everything lives inside /data, no partitions touched, and if you screw up you delete the directory and start over — you don’t even necessarily need reboot.

Went with the third. The Debian 13 image includes KDE Plasma; proot-distro is used once as an unpacker only, and proot is not involved afterwards.

Three pitfalls that decide success or failure

Anyone who doesn’t know these three points will step on all of them, and the symptoms all look like “performance is bad.”

One: you must swap Mesa. Debian’s bundled Mesa goes through the DRM msm driver, while the Android kernel only exposes /dev/kgsl-3d0. Installing the official Mesa directly gets you llvmpipe software rendering, and KWin stutters so badly it won’t move. You need to swap in the kgsl build from lfdevs/mesa-for-android-container (supports Adreno 740, made for chroot), run apt-mark hold after installing, then use glxinfo -B to confirm the renderer is FD740 / Adreno (TM) 740 and OpenGL 4.x. If all you have left is llvmpipe, it didn’t work.

Two: starting X inside the chroot requires the right posture. setenforce 0 and TMPDIR point to the chroot’s /tmp, XKB_CONFIG_ROOT points to the chroot’s xkb, and you start the X server with app_process rather than the termux-x11 command. Miss one and you get a black screen or an xkbcomp error.

Three: use the sharedUid APK of Termux:X11. If you don’t, Android will throttle Termux’s CPU because “X11 is in the foreground and Termux is in the background,” and the desktop drops frames outright. The cost is that it only accepts the GitHub-signed Termux; the F-Droid build has a different signature and can’t be installed under the same UID.

Root gives you permissions, not scheduling weight

This is the easiest one to get wrong.

Having root doesn’t mean the desktop will be smooth. Throttling and root are two separate mechanisms:

  • system_server shoves the entire process tree into the top-app / foreground / background / cached cgroups based on “whether this app is currently visible.” Processes spawned by su are still children of Termux and inherit Termux’s group; su doesn’t re-queue them.
  • The specific throttling is cpuset.cpus (background/cached get pinned to the little cores), cpu.weight (a weight difference of an order of magnitude), cgroup.freeze (the whole process tree is frozen ten seconds after entering cached). Once Termux is frozen, the X server hanging under it freezes too, and the desktop locks up.

So I added a 05-pin-priority.sh: unfreeze cgroup.freeze, raise cpu.weight to 1000, release all cores in cpuset.cpus, and pin Termux and the X server to cores with oom_score_adj=-900, renice -10, taskset.

But this is a patch, not a cure. system_server rewrites these files on every foreground/background switch; switch away once and come back and things are basically back to how they were — you have to re-run it. It only governs whether you can grab CPU; it can’t stop the freezer from freezing the processes the moment you switch away.

The real way to never fall out of the group in the first place is that sharedUid APK; the cost was covered above.

Preparation before starting

  • Install Termux from GitHub Releases or F-Droid, not Google Play (no longer updated); download Termux:X11 from nightly.
  • Set the battery optimization policy for both apps to “Unrestricted.”
  • Set aside 15 GB or more (a KDE install is about 4 GB).
  • Keep USB debugging on; if something goes wrong, adb is your rescue.
  • You need to be able to su.

Wrapping up

The desktop comes up, Chromium opens, LibreOffice opens, the terminal works — the cost is a stutter when you switch back from another app, and getting frozen if you stay in the background too long.

It has become “a tablet that can handle emergencies,” not a laptop. Put that expectation up front, and everything else is acceptable operating cost.
